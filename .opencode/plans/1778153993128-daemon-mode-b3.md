# Daemon-Mode B3 — Implementation Plan

## Scope

Translates `spec/subspecs/daemon-mode.md` from accepted-active sub-spec
into a sequenced implementation. Each task lands as its own commit,
gated on the existing `zig build test test-wpt test-test262
test-corpus test-tls test-h2` suite plus a new `test-daemon` step.

**Parent**:
`.opencode/plans/1778109534122-shiny-nebula-remainder.md` Lane B (B1
design doc accepted, B2 sub-spec accepted, this is B3).

**Companion docs (canonical)**:
- `spec/subspecs/daemon-mode.md` — what we're building
- `docs/research/2026-05-07-daemon-mode-design.md` — why those choices

If anything in this plan diverges from the sub-spec, **the sub-spec
wins**. Update both in the same change.

---

## Working rules

1. **Daemon mode is opt-in via `AWR_DAEMON=1`.** Per-process `awr
   <url>` flow stays default and unmodified throughout B3.
2. **No new spec scope.** B3 implements §2 of the sub-spec exactly.
   Any implementation gap that surfaces a need to extend §2 →
   amend the sub-spec first, then resume B3.
3. **No correctness regressions on the in-process flow.** Each task
   keeps the existing test suite green.
4. **Bottom-up.** Foundations (framing, scope cache) before
   integration (CLI wiring) before observability (bench).
5. **Each task is independently shippable.** Landing B3.1 alone
   adds a JSON-RPC framing module nobody calls — that's fine.

## Tasks

### B3.1 — JSON-RPC 2.0 framing module

| Field | Value |
|---|---|
| **ID** | B3.1 |
| **Depends on** | — |
| **Files** | `src/jsonrpc.zig` (new), `build.zig` (test wiring) |
| **Spec ref** | `spec/subspecs/daemon-mode.md §2.3` |
| **Estimate** | 2–3 hours |
| **Complexity** | Low–Medium |

**Acceptance criteria:**

1. New module exposes `Frame.read(reader, allocator)` and
   `Frame.write(writer, payload)` matching LSP-style
   `Content-Length: <bytes>\r\n\r\n<json>` framing.
2. `Request` and `Response` types model JSON-RPC 2.0 §4 / §5 with
   `id` (number / string / null), `method`, `params`, `result`,
   `error.{code,message}`. `Notification` (no `id`) supported.
3. Error codes follow JSON-RPC §5.1: -32700 ParseError,
   -32600 InvalidRequest, -32601 MethodNotFound, -32602 InvalidParams,
   -32603 InternalError, plus AWR-specific -32001 RequestTimeout
   (per sub-spec §2.3).
4. Round-trip tests: marshal a Request, frame it, parse it back —
   bytes are stable.
5. Hostile-input tests: malformed Content-Length, unterminated
   header, body shorter than declared length, nested JSON.
6. `zig build test` green.

### B3.2 — Daemon main: listen, accept loop, dispatch

| Field | Value |
|---|---|
| **ID** | B3.2 |
| **Depends on** | B3.1, B3.3 |
| **Files** | `src/main_daemon.zig` (new), `build.zig` (`awrd` exe target + `test-daemon` step) |
| **Spec ref** | `spec/subspecs/daemon-mode.md §2.1, §2.3` |
| **Estimate** | 6–10 hours |
| **Complexity** | Medium-High |

**Acceptance criteria:**

1. `zig build awrd` produces the `awrd` binary linked against the
   same `Client` / `Page` / `JsEngine` / etc. that the existing
   `awr` exe uses.
2. `awrd` listens on `${XDG_RUNTIME_DIR:-/tmp}/awrd-${UID}.sock`,
   socket file mode `0600`. Refuses to start if the socket file
   already exists and is connectable (means another daemon is
   running).
3. Single-threaded accept loop. Per-connection: read framed JSON-RPC
   request, dispatch to handler, write framed response, close
   connection. v1 serializes requests through one Client / Page —
   per the sub-spec §3 "out of scope: multi-tenant in-flight."
4. Implements all 5 v1 methods (`ping`, `fetch`, `tools`, `call`,
   `shutdown`) per `spec/subspecs/daemon-mode.md §2.3`.
5. `fetch` / `tools` / `call` results include `telemetry`
   (`SessionMetrics` JSON object) per sub-spec §2.2 ("daemon
   includes per-call SessionMetrics in its response").
6. `ping` returns `{"result":"pong","version":"<git_hash>"}` with
   `git_hash` from `build_opts.git_hash`.
7. Per-method 30 s timeout — request that exceeds it returns
   error.code = -32001 and the daemon proceeds to next request.
8. Clean shutdown on `shutdown` method or `SIGTERM`: closes socket,
   flushes per-scope jars to disk, closes `Client`, exits 0.

### B3.3 — Per-cookie-scope jar cache

| Field | Value |
|---|---|
| **ID** | B3.3 |
| **Depends on** | — |
| **Files** | `src/cookie_scopes.zig` (new) — per-scope CookieJar cache backed by disk |
| **Spec ref** | `spec/subspecs/daemon-mode.md §2.4` |
| **Estimate** | 2–3 hours |
| **Complexity** | Low |

**Acceptance criteria:**

1. New `CookieScopeCache` type wraps a `StringHashMap([]const u8 →
   *CookieJar)`. Lazy-loads `<scope>.txt` from
   `${XDG_DATA_HOME}/awr/cookies/<scope>.txt` on first access; caches
   the `*CookieJar` for the life of the daemon process.
2. `getOrLoad(scope) -> *CookieJar` is the only public accessor.
3. `flushAll()` writes every dirty in-memory jar to disk
   atomically (write to `<scope>.txt.tmp`, then rename) with mode
   `0600`. Called on idle shutdown (B3.5) and `SIGTERM` (B3.2).
4. Scope sanitization: scope names that contain `/`, `..`, or NUL
   are rejected — daemon returns -32602 InvalidParams. Mirrors
   what `cookie_path.zig` already does for the
   `$AWR_COOKIE_JAR` env var.
5. Unit tests in `src/cookie_scopes.zig`: load missing file = empty
   jar; flush + reload = same cookies; sanitization rejects bad
   names.

### B3.4 — CLI client: `AWR_DAEMON=1` path

| Field | Value |
|---|---|
| **ID** | B3.4 |
| **Depends on** | B3.1, B3.2 |
| **Files** | `src/main.zig` (gate check on `AWR_DAEMON`), `src/daemon_client.zig` (new — connect / ping / fetch wrapper) |
| **Spec ref** | `spec/subspecs/daemon-mode.md §2.2` |
| **Estimate** | 3–4 hours |
| **Complexity** | Medium |

**Acceptance criteria:**

1. New `daemon_client.zig` exposes `Client.connect(io, alloc)`,
   `Client.ping()`, `Client.fetch(url, opts)`, etc., that perform
   one round trip on the Unix socket.
2. `main.zig`'s default `awr <url>` path checks
   `std.c.getenv("AWR_DAEMON")`; when non-null and non-empty, it
   uses the new daemon client instead of the in-process flow.
3. The default `cookie_scope` is `sha1($PWD)[:12]`. Override via
   `AWR_COOKIE_SCOPE=<name>` env var.
4. Telemetry flow: daemon's response includes `telemetry`; the CLI
   client adopts it as its `SessionMetrics` and emits via the
   existing `telemetry.emit` so the user sees one record per
   invocation regardless of mode.
5. Daemon round-trip latency overhead is <2 ms median (measured
   pre/post in B3.7). `ping` round-trip < 1 ms.
6. **Per-process flow remains unchanged** when `AWR_DAEMON` is
   unset — verified by running the existing test suite.

### B3.5 — Lifecycle: spawn / flock / build-hash check / idle shutdown

| Field | Value |
|---|---|
| **ID** | B3.5 |
| **Depends on** | B3.4 |
| **Files** | `src/daemon_client.zig` (spawn-on-connect-fail), `src/main_daemon.zig` (idle timer, build-hash on ping) |
| **Spec ref** | `spec/subspecs/daemon-mode.md §2.5` |
| **Estimate** | 4–6 hours |
| **Complexity** | Medium-High |

**Acceptance criteria:**

1. **Spawn-on-first-use**: client `connect()` on `ENOENT` /
   `ECONNREFUSED` forks-execs `awrd`, waits up to 500 ms for the
   socket to appear, retries connect.
2. **Singleton via flock**: spawning client takes an advisory
   `flock` on `${XDG_RUNTIME_DIR}/awrd-${UID}.pid` before
   fork+exec. Concurrent spawners block on the lock; loser
   discovers the new socket and connects to the winner's daemon.
3. **Build-hash check**: `ping` response carries
   `version: <git_hash>`. Mismatch with client's
   `build_opts.git_hash` → client sends `{"method":"shutdown"}`,
   waits for socket to close (max 1 s), respawns, retries the
   original request.
4. **Idle shutdown**: daemon tracks last-request timestamp.
   Background `timerfd_settime` (Linux) /
   `kqueue + EVFILT_TIMER` (macOS) fires every 30 s; if last-
   request was > 5 min ago, daemon calls
   `cookie_scopes.flushAll()` and exits.
5. **Memory cap**: after each request, daemon checks
   `getrusage(RUSAGE_SELF).ru_maxrss`. If > 1 GB, refuses new
   connections (returns -32099) and exits after the in-flight
   request completes.
6. **Crash recovery**: a daemon SEGV → next CLI invocation finds a
   stale socket file. Client unlinks and respawns.

### B3.6 — `test-daemon` harness

| Field | Value |
|---|---|
| **ID** | B3.6 |
| **Depends on** | B3.4, B3.5 |
| **Files** | `tests/daemon_runner.zig` (new), `build.zig` (`test-daemon` step) |
| **Spec ref** | `spec/subspecs/daemon-mode.md §4.2, §5` |
| **Estimate** | 4–6 hours |
| **Complexity** | Medium |

**Acceptance criteria:**

1. New `zig build test-daemon` step runs the harness against an
   ephemeral `awrd` (separate `XDG_RUNTIME_DIR=/tmp/awrd-test-$$`
   per test invocation, so concurrent CI runs don't collide).
2. Cases:
   - `spawn-on-empty`: connect to an ENOENT socket → daemon spawns,
     ping succeeds.
   - `ping-version-match`: ping returns this build's git_hash.
   - `fetch-roundtrip`: fetch a local mock URL, response envelope
     matches per-process expectation.
   - `cookie-scope-isolation`: two scopes A and B, set cookie in
     A, verify B doesn't see it.
   - `cookie-persistence-across-restart`: set cookie in scope X,
     shutdown daemon, respawn, verify cookie still sent on next
     fetch.
   - `idle-shutdown`: configure daemon with 1 s idle timeout (env
     override), wait 1.5 s, verify daemon exited, next request
     respawns.
   - `build-hash-mismatch`: spoof a different git_hash on the
     client side, verify daemon is shut down and respawned.
   - `spawn-race`: 4 concurrent CLI invocations against ENOENT —
     exactly 1 daemon process exists after the dust settles.
   - `shutdown-method`: `{"method":"shutdown"}` returns `"shutting
     down"` and the daemon exits.
3. Test harness cleans up: kills any spawned daemon, removes
   socket and pid file, removes per-scope cookie dir.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| `std.posix` socket / fork APIs differ between macOS and Linux in Zig 0.16 | Medium | Test both early in B3.2; existing `src/net/tcp.zig` is the precedent |
| Daemon's single Client breaks under concurrent CLI invocations | Medium | Sub-spec §3 explicitly serializes; B3.6 race tests verify FIFO behavior |
| Cookie-scope sha1($PWD) collisions | Very low | 48 bits of cwd hash space; if it ever collides, override via `AWR_COOKIE_SCOPE=` |
| Idle-shutdown timer races with in-flight request | Medium | Idle check happens between requests, not during them; `getrusage` cap is the post-request hook |
| flock semantics on macOS APFS vs Linux | Low | `flock(2)` is POSIX advisory; both behave the same on local FS |
| H2 keep-alive across CLI invocations becomes too sticky | Low | `MAX_REQUESTS_PER_CONN = 100` already caps it; daemon doesn't change pool semantics |

## Out of scope (per sub-spec §3)

These are deferred to a future sub-spec amendment:

- Multi-tenant concurrent in-flight requests within one daemon
- Per-scope TLS identity (client certs, etc.)
- IPC channel auth beyond Unix socket file mode
- Network-exposed daemon
- Pre-warming connections to known hosts on daemon start

## Closure criteria

The plan is closed when **all** of the following hold:

1. B3.1–B3.7 acceptance criteria all met.
2. `zig build test test-wpt test-test262 test-corpus test-tls
   test-h2 test-daemon` all green.
3. `AWR_DAEMON=1 awr <url>` round-trips through the daemon for
   every shipped subcommand path (default URL, `render`, `tools`,
   `call`).
4. `AWR_DAEMON=` (unset) flow continues to behave identically to
   pre-B3 — verified by the diff of test outputs.
5. Bench shows ≥30% wall-clock improvement on the 5-fetch chain.
6. Closure record appended to this file with measured numbers.
7. This file moves to `.opencode/plans/archive/` once closure is
   recorded.
