# AWR Performance Optimization Plan

## Problem
AWR page loads are 1.7-3.1x slower than Playwright/Chromium. The goal is to make AWR fast enough to be practically useful for agent workflows without adopting Blink.

## Root Cause Analysis

| Bottleneck | Impact | Fix Complexity |
|---|---|---|
| **No connection reuse** — every HTTP request does full DNS+TCP+TLS handshake | ~40-60% of page load time | Medium |
| **Full JS engine rebuild per navigation** — Runtime+Context destroyed and recreated | ~15-20% | Low |
| **Debug mode compilation** — QuickJS-NG compiled with -O0 | ~20-30% JS slowdown | Low |
| **Overly generous drainAll timeouts** — 2x 5-second windows | Up to 10s wasted on timer-heavy pages | Low |
| **Blocking external script fetches** — scripts execute sequentially, each blocking | ~20-40% on script-heavy pages | Medium |

## Priority 1: Connection Reuse (Biggest Win)

**Problem**: `client.zig` creates a new `std.http.Client` per request. The `ConnectionPool` exists but is never used.

**Fix**: Wire the existing `ConnectionPool` into the fetch path.

### Steps:
1. **`src/client.zig`**: Modify `fetchOnceStd()` to use a persistent `std.http.Client` instance stored on `Client` struct (not created per-request)
2. **`src/client.zig`**: For the BoringSSL path, keep TCP connections alive in the pool and reuse them for subsequent requests to the same origin
3. **`src/net/pool.zig`**: The pool already has Chrome limits (6/origin, 256 total, 30s idle timeout) — just needs to be wired in
4. **`src/page.zig`**: The `Page.client` already owns a `Client` — reuse it across all fetches (page HTML + external scripts + inline fetch calls)

**Expected gain**: 40-60% reduction on multi-request pages (script-heavy sites)

**Files to modify**:
- `src/client.zig` — persistent HTTP client, connection reuse
- `src/net/pool.zig` — ensure pool is thread-safe enough for single-threaded use
- `src/net/tcp.zig` — make connections reusable (currently one-shot)

## Priority 2: JS Engine Reuse Across Navigations

**Problem**: `processHtmlWithOptions` calls `self.js.deinit()` + `JsEngine.init()` — full teardown/rebuild of QuickJS Runtime, Context, and all polyfills.

**Fix**: Instead of destroying the runtime, reset the context and re-inject globals.

### Steps:
1. **`src/js/engine.zig`**: Add `JsEngine.reset()` method that:
   - Frees all global properties from the context
   - Re-evaluates polyfills (console, timers, fetch, URLSearchParams, structuredClone)
   - Does NOT destroy the Runtime (expensive)
2. **`src/page.zig`**: In `processHtmlWithOptions`, call `js.reset()` instead of `deinit()` + `init()`
3. **`src/dom/bridge.zig`**: Ensure `installDomBridge` is idempotent (can be called after reset)

**Expected gain**: 15-20% reduction per navigation

**Files to modify**:
- `src/js/engine.zig` — add `reset()` method
- `src/page.zig` — use `reset()` instead of deinit/init
- `src/dom/bridge.zig` — ensure clean re-installation

## Priority 3: Reduce drainAll Timeouts

**Problem**: Two 5-second drain windows (10s total potential wait). Most pages have no timers.

**Fix**: Use adaptive timeouts.

### Steps:
1. **`src/page.zig`**: Change drainAll calls:
   - After DOMContentLoaded: `drainAll(1_000)` (1 second)
   - After window load: `drainAll(2_000)` (2 seconds)
2. **`src/page.zig`**: Add `drainAllQuick()` method that uses `tickNoWait()` instead of `tickOnce()` — only fires already-expired timers, doesn't block waiting
3. Use `drainAllQuick()` for the interactive phase, full `drainAll(2000)` for the load phase

**Expected gain**: Eliminates worst-case 10s hang; typical pages unaffected (they drain quickly)

**Files to modify**:
- `src/page.zig` — reduce timeouts, add quick drain

## Priority 4: Build in Release Mode

**Problem**: Default `zig build` uses Debug mode (-O0). QuickJS-NG's bytecode interpreter runs 2-3x slower without optimization.

**Fix**: Default to ReleaseSafe for better performance.

### Steps:
1. **`build.zig`**: Change `standardOptimizeOption` default from Debug to ReleaseSafe
2. Update README to recommend `zig build -Doptimize=ReleaseSafe` as the default

**Expected gain**: 20-30% faster JS execution, 10-15% faster overall

**Files to modify**:
- `build.zig` — default optimization level
- `README.md` — update build instructions

## Priority 5: Parallel External Script Fetching

**Problem**: External scripts execute sequentially. Each `src=` blocks the pipeline.

**Fix**: Fetch all external scripts in parallel, then execute in document order.

### Steps:
1. **`src/page.zig`**: In `executeScriptsInElement`, first pass: collect all external script URLs
2. Fetch all external scripts concurrently using the connection pool
3. Second pass: execute scripts (inline + fetched) in document order

**Expected gain**: 20-40% on script-heavy pages (Hacker News, Wikipedia)

**Files to modify**:
- `src/page.zig` — parallel fetch, ordered execution

## Implementation Order

1. **Priority 4** (Release mode) — 5 min, immediate 20-30% gain
2. **Priority 3** (Reduce drainAll) — 15 min, eliminates worst-case hangs
3. **Priority 2** (JS engine reuse) — 1-2 hours, 15-20% gain
4. **Priority 1** (Connection reuse) — 2-3 hours, 40-60% on multi-request pages
5. **Priority 5** (Parallel scripts) — 2-3 hours, 20-40% on script-heavy pages

Combined expected improvement: **2-4x faster** page loads, bringing AWR into the same ballpark as Chromium for DOM+text extraction.

## Closure record (2026-05-04)

**P1–P4 landed, P5 deferred.** Status corrected from the original plan
because P1 as initially shipped (commit `7cdba9f`) didn't deliver.
Two follow-ups (`38d8dfd`, `22c3541`) found and fixed the actual
blockers, plus documentation (`1d25a33`) and tests (`80f7fe2`,
`5a8e36e`).

### What changed vs the plan

The plan attributed AWR's slowness primarily to absent connection
reuse and assumed P1 would deliver "40-60% on multi-request pages."
That was the right intuition but the wrong implementation:

- **`std.http.Client`'s pool was already there** — but every connection
  was being destroyed by `Request.deinit` because chunked + gzip
  responses leave the underlying transfer reader off `.ready`. P1
  shipped without exercising it, so the original test pass didn't
  catch the regression. Fixed in `38d8dfd` by draining
  `req.reader.interface` after `streamRemaining`.

- **Most production traffic doesn't use std.http.Client at all.**
  Fingerprint-sensitive sites (HN was 100% on this path) fall back to
  `fetchOnceBoringSslHttp1`, which had no keep-alive whatsoever
  (HTTP/1.0 + `Connection: close`). P1 didn't address this. Fixed in
  `22c3541` by adding `BoringSslPool` and switching to HTTP/1.1.

- **Every BoringSSL request was paying ~100-160ms for a doomed std
  attempt first.** `fetchOnce` always tried `fetchOnceStd` before
  falling back. For hosts that always fail (HN), this was pure waste.
  Fixed by `Client.std_tls_failed_hosts` cache in `22c3541`.

### Final measurements (warm, in-process processHtml time)

| URL       | Before       | After       | Δ      |
|-----------|--------------|-------------|--------|
| HN        | 437ms        | **90ms**    | -79%   |
| Wikipedia | 134ms        | 104-123ms   | -22%   |
| MDN       | 355ms        | 323-332ms   | -8%    |
| example   | 7ms          | 7ms         | flat   |

Wall-clock (process start → exit, warm):

| URL       | Plan baseline | Plan target | Final     | Status       |
|-----------|---------------|-------------|-----------|--------------|
| example   | 196ms         | < 200ms     | 193ms     | ✅ HIT       |
| HN        | 706ms         | < 400ms     | 590ms     | -44%, missed |
| Wikipedia | 917ms         | < 500ms     | 403ms     | ✅ HIT (-56%)|
| MDN       | 932ms         | < 500ms     | 510ms     | -45%, ~at    |

The HN target miss is inherent to the BoringSSL path — the *first*
request still pays the full TCP+TLS handshake (~340ms via curl). Only
sub-resources within the same session benefit from keep-alive. Going
below 400ms for an HN cold load would require HTTP/2 multiplexing
(nghttp2 is already vendored for the JA4 work) or a warm-cache mode.

### Why P5 (parallel script fetch) is still deferred

The original plan listed P5 as the 5th priority for a 20-40% gain on
"script-heavy" pages. With the BoringSSL pool now in place:

- HN and Wikipedia have 1 external script each — parallel fetching
  doesn't help them.
- MDN has multiple, but its bottleneck is a single 661ms
  cross-origin script (`transcend-cdn.com/.../airgap.js`) that
  parallel fetching cannot speed up — it's the long pole.
- AWR's HTTP client is single-threaded; parallel fetch needs either
  OS threads or libxev async, both with non-trivial blast radius.

The bench data argues for keeping P5 deferred unless a clear
script-heavy use case appears that isn't currently met.

## Closure record — P5 reopened and landed (2026-05-05)

**P5 ended up unblocked after profiling github.** The earlier closure
note argued P5 was unnecessary because none of the original benchmark
URLs had a script-heavy bottleneck that parallelism could fix. That
held for the original four URLs but missed a real workload: github
issue/repo pages ship 60+ same-origin scripts, and AWR's
sequential-with-keep-alive path was spending ~3 seconds in `scripts`.
Connection reuse trims per-request RTT but can't hide 60 round-trips
in series.

### What landed

- **`ScriptPrefetchCache`** in `src/page.zig` — `StringHashMapUnmanaged`
  guarded by an atomic `SpinLock`. Workers process disjoint URL
  strides, so contention is rare and a syscall-free spin lock beats a
  Mutex's overhead.
- **`prefetchExternalScripts`** — DOM walk collects unique
  http(s) `<script src>` URLs in document order, then fans out to up
  to 6 worker threads. Below 4 URLs the orchestration cost outweighs
  benefit and the path falls back to per-script sequential fetch.
- **`prefetchWorkerMain`** — each worker creates its own
  `std.Io.Threaded` instance and `Client`. The shared-`Io` design
  triggered ISCONN panics inside `groupAsync`'s happy-eyeballs DNS
  scheduler; per-worker instances are independent and cheap.
- **`runExternalScript`** — looks up `cache.get(resolved)` first,
  falls back to a direct main-Client fetch on miss. Cached bodies are
  borrowed (not duped); they live until `processHtml` returns.

### Cookie limitation

Each worker has its own cookie jar and `std_tls_failed_hosts` cache.
`Set-Cookie` headers from script responses do **not** propagate to the
main `Client`. Acceptable for static page rendering; revisit if a
real auth-gated subresource scenario appears. `persist_cookies` is
forced off on workers — concurrent file writes to one jar would race.

### Measurements (warm, total wall-clock)

| URL              | Before P5  | After P5   | Δ      |
|------------------|------------|------------|--------|
| github (zig repo)| ~3000ms    | **1238ms** | -59%   |
| MDN              | 323-332ms  | 253ms      | -22%   |
| Wikipedia        | 104-123ms  | 104ms      | flat   |
| HN               | 90ms       | 92ms       | flat   |
| example          | 7ms        | 11ms       | +4ms*  |

*example.com has no external scripts; the prefetch DOM walk + fixed
overhead shows up as a few extra ms.

### What I didn't do

- **HTTP/2 multiplexing for sub-resources.** Same-origin script
  fetching from github could be one stream-multiplexed connection
  instead of N parallel TLS handshakes. Currently each worker still
  pays a TLS handshake per host. nghttp2 is vendored for the main
  fetch path; wiring sub-resources through it would be a separate
  optimisation pass.
- **Cookie jar fan-in.** Skipped per the limitation above.

### Files (P5)

- `src/page.zig` — `ScriptPrefetchCache`, `SpinLock`, `PrefetchWorker`,
  `prefetchWorkerMain`, `prefetchExternalScripts`,
  `collectExternalScriptUrls`. `runExternalScript` and
  `executeScriptsInElement` now take an optional cache pointer.
  `TimingProbe` adds `prefetch=` and `ext_cache=` markers.
